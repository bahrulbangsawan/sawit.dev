# Speedups of the 500-line split (2026-11-02)

Every `perf(...)` commit since 6935d18, by feature: what got faster and its lane's before -> after numbers (each commit's subject and body say how it was measured). Lanes measured with thread CPU time or wall time, median of 7 or more runs, old and new binaries in turns; many could only measure the debug build (their shared release-bench slot had an hour's queue). Afterwards 74 of the 74 Rust speedups were measured again, apart from their lanes, in an optimized build (`--release`, LTO off, 16 codegen units) on the final code, against the final code with the commit (or its group) reverted: the last column. Those that save processes or run them at once were timed on the wall clock; those that move work off the UI thread, by how long the UI thread is held. The site's byte savings were measured again the same way, apart from their lane: the final production build against the final site with its seven site commits reverted.

Every code change was reviewed for a change anyone could see; the six dropped and the eight fixed after review are in `2026-11-02-split-open-items.md`.

## How the optimized-build numbers were taken

13 agents, one per crate group, each built the crate's tests optimized (`cargo test --release`, LTO off, 16 codegen units) twice: the final code, and the final code with the group's speedups reverted (or only the commit itself where another in the group shares its path). The same throwaway harness ran in both, timing thread CPU time, median of 7 runs (wall clock where the work runs in other processes), the two binaries in turns for 3 to 25 rounds; outputs were checked identical between the two trees. The scenarios, per commit:

- <a id="de9f6b5"></a>`de9f6b5`: Design panel, Colors tab: one DesignPanel::render over a scan at the page script's caps (500 colours, 400 text samples, 400 assets, 500 variables). Test: browser::bench_release::colors_tab_render Optimized: 22.30 ms -> 2.42 ms (faster). Debug, as the lane measured: Colors median 732.7 ms -> 23.1 ms per render; the first render (builds the palette) 32.0 ms Notes: 9.2x faster (the debug build showed 31.7x). The first render of a new scan, which builds the palette in the after tree, went from 22.55 ms to 3.20 ms. The after value was lower in all 7 paired rounds. A first pass (5 rounds, 1-min load 8-10, binaries without the control lines) gave 22.70 -> 2.48 ms. The big_scan fixture is the lane's own, copied from its surviving scratch file.
- <a id="f74ab98"></a>`f74ab98`: Annotate panel: one AnnotatePanel::render with 30 notes like real picks (60 computed styles, ~1.7 KB of markup, 12 attributes, DOM path, neighbours and source each; 10 notes on each of 3 pages). Test: browser::bench_release::annotate_panel_render Optimized: 283.3 us -> 163.8 us (faster). Debug, as the lane measured: median 2.086 ms -> 1.334 ms per render (min 1.478 -> 1.279 ms) Notes: 42% less time per render. The after value was lower in all 7 paired rounds. The first pass gave 294.3 -> 172.1 us. The lane's original note fixture had been dropped and was not in the scratchpad, so these notes are rebuilt from the commit body's description. Absolute numbers may differ from the lane's notes.
- <a id="c5e7bcc"></a>`c5e7bcc`: Pull request thread, one ThreadView::render on the Timeline tab with a synthetic 200-event timeline (runs of commits, comments and reviews with ~1 KB bodies). Test: git::thread::bench_release::thread_timeline_render Optimized: 1321.0 us -> 1272.8 us (faster). Debug, as the lane measured: 143 us -> 0 per render at 200 events: one grouping 71 us, done twice per render before and not at all after (100 events 36 us, 500 events 150 us per grouping) Notes: 48 us (3.7%) less per whole render. The after value was lower in all 7 paired rounds, and in all 5 rounds of the first pass (1318.7 -> 1263.2 us). Control, same code in both binaries: one github::group of 200 events takes 10.9 us, so the two groupings before were about 22 us; the rest of the saving is presumably freeing those copies. At 500 events: 3290.1 -> 3138.5 us (4.6%), with one grouping at 25 us. The debug figure timed the grouping alone; this one is the whole render, where the grouping is a small part.

Control, same in both binaries: one search takes 29.1 us ("review"), 58.5 us ("unclear tests") or 1.6 us (no query). The frame saving is larger than one search: the old code also searched again in the list's callback and copied each visible row's prompt, body and all. That is not broken down further.
