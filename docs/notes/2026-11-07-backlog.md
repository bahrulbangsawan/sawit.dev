## Ground rules

1. **One item at a time, one commit per item** (Conventional Commits, as in `git log`). Run
   `cargo fmt`, `cargo clippy --workspace` and the tests of the crates you touched before each
   commit. Do not push or release.
2. **Keep the app and the MCP server in step.** A feature an agent would want gets a `sawit` MCP
   tool (or a code-mode API, after item B1), and a line in the README's MCP table.
3. **Test in the real app** with Sawit's own tools (`app_state`, `terminal_*`, `browser_*`,
   `canvas_*`, `browser_screenshot`). Unit tests alone are not enough for UI work.
4. **No feature is lost.** Every move to Rust and every size or RAM saving keeps behaviour the
   same; the e2e specs (`e2e/specs/`) still pass.
5. **Only the user moves the keyboard** (`crates/app/src/browser/engine/keyboard.rs`, commit
   `bdca7d5`). Nothing here gives a web view the keyboard because an agent asked.
6. **Rust first, for every item.** Build each feature in Rust: logic in `crates/core`, UI in
   GPUI (`crates/app`, `vendor/gpui-base`), Apple frameworks through `objc2-*`. Prefer
   pure-Rust crates, and reuse those already in the workspace (`rusqlite`, `security-framework`,
   `html5ever`, `image`, `rmcp`, `rustls`, `tokio`) before adding new ones. Use something else
   only where Rust can't do the job, or does it clearly worse (size, speed or correctness), and
   then pick the best option:
   - **JavaScript** only inside a web page, where WebKit allows nothing else (see Part A), and
     for vendored bundles that are JS by nature (`pele.global.js`, mesurer).
   - **A C library or Apple framework** called from Rust, when it beats every Rust crate (for
     example VideoToolbox for video encoding).
   - **No Node, Python or other runtime** at run time, and no shelling out to `npx`, `curl` or
     another CLI when a Rust crate or an HTTP API can do the same. The exception is a tool the
     user already runs, such as an agent's own CLI that has no API.
   - Write down each non-Rust choice and why in the item's commit message.
7. **No outside brand names in commits or in the app's text.** Commit messages, UI labels,
   tooltips, empty states, MCP tool names and descriptions, and README copy never name the
   products or sites a feature was modelled on (the reference scanners in B8.1, the usage
   tracker in Part C, the code-mode reference in B1). Describe the feature itself. Names in this
   backlog are for research only. Platforms a feature actually works with may be named where
   the user needs them, for example "WhatsApp preview" or a provider's account name.

# Part A: move page JavaScript logic to Rust

**Status (2026-11-07):** not started. Every file named below is still JavaScript, and the
references still hold (`mesurer::files::avc_codec_for` at `files.rs:348`, `dataBlob` in
`mesurer/files.js`, the AVC level table in `mesurer/capture.js`).

Background: the page scripts in `crates/core/src/browser/page/` (about 4.6k lines) run inside
WebKit, which only runs JavaScript. A 100% Rust rewrite is not possible: Rust compiled to WASM
would still need JS glue for every DOM call, a page's CSP can block WebAssembly, and debugging
gets harder. The plan is a **thin JS layer that collects facts or applies changes, with the
logic in the Rust host**. Items are in the order to do them.

### Must stay JavaScript (do not move)

- `agent/network.js`, `agent/console.js`, `agent/scripts.js`: they patch `fetch`,
  `XMLHttpRequest` and `console` inside the page.
- `agent/ipc.js`, `agent/ops.js`, `agent/url.js`: the bridge to Rust.
- `mesurer/*` (except A2): it replaces the browser APIs mesurer calls (`navigator.clipboard`,
  `ClipboardItem`, `EyeDropper`, `getDisplayMedia`, `<a download>.click()`, `window.open`,
  `persistence`). Some must answer synchronously: the keydown `handOver` in `keys.js` must
  `preventDefault()` during dispatch, `persistence.load()` must be synchronous, recordings must
  be a JS `MediaStream`. The real work already happens in Rust.
- The four entry files (`agent.js`, `design.js`, `overlay.js`, `mesurer.js`), and the vendored
  `crates/core/assets/pele/pele.global.js` and `vendor/mesurer/bundle/*`.

## A1. `design/color_math.js` → Rust (116 lines, low risk)

- **Why:** it is pure (no DOM) and is already tested from Rust in QuickJS
  (`crates/core/src/browser/tests/design.rs`), so those tests can be reused.
- **Move:** parsing CSS colors (rgb, hex, oklch, oklab, lab, lch, `color(srgb | srgb-linear |
  display-p3)`) to sRGB, and OKLCH chroma.
- **Also:** the color parsing in `design/colors.js`. Its canvas fallback for unusual syntax stays JS.
- **Watch:** `scan.js` uses the color math during the walk (the opaque background behind an
  element, skipping colors that aren't chromatic). The page may need to send back raw style
  strings and let Rust filter them. Measure payload size on large pages (apple.com).
- **Done when:** the design tests pass against the Rust version, and `browser_design` output is
  the same on a few real sites before and after.

## A2. Remove the mesurer glue's duplicates (about 30 lines, trivial)

- `mesurer/capture.js`: the H.264 level table and `avcCodecFor` duplicate
  `mesurer::files::avc_codec_for` (`crates/core/src/browser/mesurer/files.rs:348`). Ask Rust
  once before a recording starts, through the bridge.
- `mesurer/files.js`: `dataBlob` decodes `data:` URLs. Send the raw `href` with `file.save` and
  decode it in Rust.
- **Done when:** a recording and a screenshot save still work (`e2e/specs/mesurer.test.js`).

## A3. Rest of the design logic: `rules.js`, `limits.js`, `helpers.js` (about 70 lines)

- Grouping, ranking and size limits on the scan's results move to Rust.
- **Stays JS:** `scan.js`, `style.js`, `stylesheets.js`, `fonts.js`, `html.js`, `boxes.js`. They
  read the DOM, CSSOM or `document.fonts`. They can shrink to "collect and send".

## A4. Element snapshot formatting (`agent/elements.js`, part of 229 lines)

- **Move:** building the outline text, assigning refs, clipping and describing elements. The page
  sends structured data (role, name, value, state, depth) and Rust builds the snapshot. Rust can
  then also diff two snapshots.
- **Stays JS:** walking the DOM and shadow roots, accessible names, visibility, and the
  ref-to-element map the page needs to act on a ref.
- **Done when:** `browser_snapshot` output is identical on the fixtures in
  `docs/fixtures/browser/` and on a few real sites.

## A5. Native pointer events for visible tabs (`agent/pointer.js`, 95 lines)

- **Move:** `click` (single, double, right), `hover` and scroll are sent as real `NSEvent`s to the
  `WKWebView`, so the page gets trusted events (`isTrusted: true`): real `:hover`/`:active`,
  native controls, and sites that ignore synthetic events.
- **Catch:** native mouse events need the view on screen, in a window and not hidden. Agents
  now drive background tabs through JS. **Keep the JS path as a fallback** when the tab isn't
  visible.
- **Stays JS:** finding the target point (`aim`, `hitTest`: `getBoundingClientRect`,
  `elementFromPoint`).
- **Must not:** move the pointer the user sees, or give the web view the keyboard.

## A6. Native keyboard events (`agent/keyboard.js`, `press` only); needs a decision first

- **Gain:** trusted key events, and the hand-made imitations can go (Tab cycling with
  `tabbables()`, `execCommand("insertText")`, PageUp/PageDown scroll amounts).
- **Blocker:** native key events only reach a page when the `WKWebView` is first responder,
  which `crates/app/src/browser/engine/keyboard.rs` forbids for an agent's tool call. Sending
  `keyDown:` straight to the view without first responder is unreliable for text input
  (`NSTextInputClient`). **Ask the user before changing that rule.** Until then, leave this item.
- **Stays JS in any case:** `type` (and `setValue` for React-controlled inputs) and `select` for
  `<select>` options.

## A7. Native overlay drawing (`overlay/*`, about 1.7k lines); do last

- Markers, highlights, agents' cursors and the popover could be a GPUI layer over the web view.
- Picking, events and selectors (`picking.js`, `events.js`, `selectors.js`) and a feed of element
  positions while scrolling and resizing would stay JS.
- Keeping a native layer in sync with page scrolling and animation is hard, and mesurer's
  layering is tied to Sawit's overlay z-index (`mesurer/host.js`).
- **Rust first, in steps:** after A1–A5, move the parts that don't follow page scrolling first
  (the popover, agents' cursors, the toolbar), then try highlights and markers behind a setting.
  Keep the JS overlay for anything that lags or drifts behind the page, and say so in the
  commit.

### Estimate

A1–A5 move about 600–800 lines to Rust. With A6 and A7, about 2.5k. The JS left is only what a
page can run.

# Part B: MCP, UI and features

## B1. Audit every MCP tool, full control of Sawit through MCP, and a code-mode MCP

**Goal:** check that every app feature has a working, consistently named MCP tool, so an agent
can control all of Sawit. Then cut the token cost of the large tool list: today every agent
loads every tool schema, even the ones it never uses. Add a code-mode MCP, where the agent finds
the functions it needs and runs a short script that calls them.

**Where things stand:** not started. `crates/mcp` has 163 `#[tool]`s, there is no audit note
and no code mode, and `boa_engine` is not in the tree (`rquickjs` 0.14 is, in `crates/core`).

- **Audit:** list every tool in `crates/mcp` against every app feature. Note features with no
  tool, tools that overlap, and tools whose names or arguments are inconsistent.
- **Full control:** every app feature an agent would use can be driven through MCP.
- **Code mode:** there are too many tools for an agent's context. Expose a small set instead,
  for example `search_api` (find functions by keyword and read their typed signatures) and
  `run` (run a short script that calls those functions), so an agent writes code against a typed
  Sawit API instead of loading 200 tool schemas. Keep the old tools behind a setting until code
  mode is proven.
- **How it works** (reference for research: the `search` + `execute` tools of the
  `cloudflare-api` MCP; don't name it in commits or UI). The agent sees two or three tools
  whatever the size of the catalog. A script can call many Sawit functions in a row (e.g. run a
  command, read its output and then screenshot the browser) and return only the result, so the
  intermediate results never use the agent's tokens. Generate the typed signatures in Rust from
  the same tool definitions in `crates/mcp` (`rmcp`), so the two can't drift apart. Measure the
  tokens used on `tools/list` before and after, and put the numbers in the audit note.
- **Script runtime, Rust first.** Agents write JavaScript or TypeScript best, so scripts stay
  JS, but the engine should be Rust. Try **Boa** (`boa_engine`, a JS engine written in Rust)
  first. Fall back to `rquickjs` (QuickJS, a C engine, already in `crates/core` for Pele) only
  if Boa is too slow, too big (B6) or misses language features agents use (`async`/`await`,
  modules, JSON). Compare the two in the audit note: binary size, start time and the time a
  typical script takes. Either way, run scripts in a sandbox with no file or network access
  except through Sawit's functions, with a time and memory limit. Strip TypeScript types in
  Rust (for example with `swc` or `oxc`) if agents send TypeScript.
- **Done when:** the audit is written up in `docs/notes/`, the gaps are closed, and an agent can
  finish the e2e flows through code mode with only the code-mode tools loaded.

## B2. Animated activity icons on terminal, browser and canvas tabs

**Goal:** each terminal, browser and canvas tab shows its state at a glance (idle, running,
stopped and so on) with a small icon that animates while work is in progress.

**Where things stand:** terminal tabs already show some state, but none of it moves. The glyph
turns the success colour while an SSH session or a script runs, agents' logos show with a dot over
them (`crates/app/src/terminal/panel/render.rs`), and an exited pane gets an "(exited)" title and a
banner (`terminal/tab/header.rs`), with no exit code. Browser tabs swap the globe for a static
`LoaderCircle` while loading (`crates/app/src/browser/tabs/strip.rs`), and `browser_tabs` reports
`loading`. Canvas tabs show no state. What is left: one set of states for all three tab kinds,
the animation, success or failure from the exit code, "needs attention", and the state in
`app_state`.

- States to show at least: idle, running or busy (a command running, a page loading, an agent
  drawing), stopped or exited (with the exit code: success or failure), and needs attention.
- Animate only while running, keep it subtle, and respect Reduce Motion.
- Draw and animate the icons in GPUI (Rust), with no web view, Lottie file or GIF.
- Expose the same state to agents (`app_state`).

## B3. Agents reuse terminals instead of opening new tabs

**Goal:** agents stop leaving dozens of terminal tabs behind. An agent reuses its latest idle
terminal for the next command, or closes a terminal it opened once the command is done.

**Where things stand:** `terminal_run` without `new_tab` or `cwd` already types into the
*active* idle shell, unless the user is typing in it (`Command::TerminalRun` in
`crates/app/src/workspace/control/mod.rs`, `TerminalRunArgs` in
`crates/mcp/src/app/terminal.rs`). Any `cwd` always opens a new tab, though, and the shell
reused is the active one, not the agent's own latest. Tabs can already be locked and pinned
(`terminal/panel/lock_pin.rs`), and `terminal_close` with `scope: "idle"` is Safe Close All.
What is left: reuse the agent's own latest idle terminal (also when `cwd` matches its folder),
skip tabs running a dev server and locked or pinned tabs, close one-off tabs while keeping
their output readable, and the optional cap.

- `terminal_run` reuses the agent's most recent idle terminal (prompt showing, no command
  running) before opening a new tab. Never reuse a terminal the user is typing in, one with a
  dev server running, or a pinned or locked one.
- A one-off command's tab can close itself when it finishes, with its output still readable
  through `terminal_read` for a while.
- Optional: a cap on agent-opened tabs per project.
- **Done when:** an agent running 50 commands in a row leaves one or two tabs, not 50.

### B4.1. Zoom to fit while an agent draws, and a "Follow agent" button

**Goal:** you can watch an agent draw without chasing it around the canvas. When an agent starts
working, the view zooms to fit the content, and a "Follow agent" button keeps the view on
whatever the agent is changing, as it happens.

- **Zoom to fit by default:** when an agent starts working on the canvas (`canvas_begin`, or
  the first write in a session), fit the view to the page's content once, with animation. If
  the user pans or zooms after that, leave the view alone until the next agent session.
- **Follow agent:** a toggle on the canvas toolbar, on whenever an agent is active. While it is
  on, the view moves smoothly to each shape the agent adds or changes as it happens (pan, and
  zoom out only if the shape would be off screen), and the shapes being worked on are marked.
  Group quick changes in one move (about 150 ms) so the view doesn't shake. Panning or zooming
  by hand turns follow off, and the button shows it is off. If several agents draw at once,
  follow the newest change, or let the user pick one agent.
- Respect Reduce Motion: jump without animating.
- **MCP:** the agent can read the follow state, but only the user turns it on or off.
- **Done when:** an agent drawing a 30-shape diagram stays on screen from start to finish with
  follow on, and one manual pan stops the view from moving.

### What moves

- ⌘J (`ToggleTerminal`) is freed; ⌘T does its job. Leave ⌘J unbound.
- `ToggleSidebar` moves from ⌘B to ⌘E.
- `NewTerminal` moves from ⌘T to ⌥⌘T, in the menu too.
- ⌃⌘N is removed; `OpenNewProject` moves to ⌘⇧N.
- `NewWindow` loses ⌘⇧N; give it ⌥⌘N and keep it in the File menu. ⌥⌘N is `NewFolder` while the
  file tree has focus; the tree keeps it there, as ⌘N stays `NewFile`.
- `CloseOtherTabs` loses ⌥⌘T to `NewTerminal`. It stays in the tab menu and moves to a free
  ⌘K chord, next to its siblings (⌘K E, ⌘K T, ⌘K U, ⌘K W).
- ⌃⌘C (`OpenCanvas`) stays as a second way to open the canvas.
- ⌘⇧J stays `ToggleCenter`. ⌘⇧T is "reopen closed tab" in browsers and editors; if Sawit adds
  that later, give it another key.

### Behaviour

- **Open/close:** the key shows the area if it is hidden (opening it first if the project has
  none, for example the canvas), and hides it if it is shown. Hiding moves focus to what is
  left, never to nothing.
- **Full screen already exists** (`0c16005`, `2d17d38`): `MaximizeTerminal`, `MaximizeBrowser`
  and `MaximizeCanvas` on ⌃⌘1/2/3, ⌘⇧↩ (`ToggleMaximizePane`) for the focused one, Escape

  the same key brings the layout back. It is not macOS full screen (⌃⌘F stays the system's).

- **⌘N new file:** makes a file in the folder selected in the file tree, else in the project's

  Places that have their own ⌘N keep it while they have focus (the keymap editor's

- **⌘⇧N new project:** opens the New Project page (`OpenNewProject`).

- **Local keys win while their place has focus.** ⌘B is bold while editing text on the canvas

  else uses it (the tab bar or a panel's header has focus); inside a terminal or an editor it

### B8.1. Agent-readiness checks in the SEO/AEO scanner

**Goal:** make Sawit's scanner at least as complete as the dedicated agent-readiness scanners.
Study how they work, gather every check they run, and add them to Sawit's SEO/AEO scanner.
Rewrite the checks in Rust first. Call an outside service's API or MCP server only for what
Sawit can't check itself. The scan must work on both local and production URLs.

**References, for research only** (never named in commits, UI text or MCP descriptions; see
ground rule 7). What a first look found (2026-11-07). Check again before you build, because
these scanners change their checks often:

- **isitagentready.com:** 22 checks in 5 groups. *Discoverability:* `robots.txt`, sitemap,
  `Link` discovery headers, DNS for AI Discovery (DNS-AID). *Content accessibility:* Markdown
  through content negotiation. *Bot access control:* AI bot rules in `robots.txt`, Content
  Signals, Web Bot Auth. *Protocol discovery:* API Catalog, OAuth discovery, OAuth Protected
  Resource (RFC 9728), `auth.md`, MCP Server Card, A2A Agent Card, Agent Skills, WebMCP, ARD
  manifest, Personal Agent Protocol. *Commerce:* x402, MPP, UCP, ACP. It has three scan types
  (all, content site, API or app) and lets you pick checks. Its page names no API, no MCP and
  no scoring formula.
- **agentready.org:** a spec and directory of scanners, not a scanner. It points to ora.ai,
  is-agentic.com (`npx is-agentic`), Mintlify Agent Score (29 checks, `npx mint score`) and
  Netlify AXIS (`npx @netlify/axis`). Read its spec for the check definitions it shares with
  these tools.
- **ora.ai:** 132 checks in 4 layers, weighted discovery 20, access 30, usability 40,
  payments 10, giving a 0 to 100 score and a grade from A+ to F. Its "Essentials" score for
  content sites gives required checks 80 points, recommended checks 20, and up to 5 more for
  forward-looking signals. Checks that don't apply, and "emerging" checks, are left out of the
  total. Payment protocols count if any one of them is supported.
  - Catalog: `GET https://ora.ai/api/checks` returns every check's id, name, description,
    layer, `maxScore`, tier, maturity, `specUrl` and `recommendation`. Use it as the source
    list.
  - API: `POST /api/scan`, `GET /api/scan/stream` (SSE), `POST /api/scan/checks` (chosen
    checks only), `GET /api/score/{domain}`, `GET /api/openapi.json`. Reading needs no key.
  - MCP: `https://ora.ai/api/mcp` (streamable HTTP, with a `list_checks` tool).
  - CLI: `npx ax audit <url> --json`.
  - It scans only public URLs. For localhost it needs a tunnel (`ax audit localhost:3000
    --tunnel-cmd '...'`).

What to build:

- **One list of checks.** Merge the three sources into one table in `crates/core`, keyed by
  check id. Each check records its source, layer or group, tier (required, recommended,
  bonus), what it fetches, how it passes, and how to fix it. Remove duplicates (`robots.txt`,
  sitemap, `llms.txt`, JSON-LD, Markdown negotiation, MCP Server Card, A2A card, OAuth
  metadata, `auth.md`, WebMCP, payments and so on) and merge them with B8's SEO checks so a
  check never runs twice. Write the table up in `docs/notes/` too.
- **Run the checks in Rust (the main path).** Rewrite every check that one HTTP request, a
  DNS lookup (a Rust resolver such as `hickory-resolver`, for DNS-AID records) or the loaded
  page can answer. Probe MCP endpoints with `rmcp`'s client. Examples: the `.well-known` files, `Link` headers,
  `Accept: text/markdown` with `Vary`, `robots.txt` rules for each AI user agent, Content
  Signals, `llms.txt` structure and whether its links load, the page's token budget, JSON-LD
  coverage, redirects, 404s that agents can read, the accessibility tree (names, labels, native
  controls), and the MCP endpoint's `initialize`/`tools/list` with tool naming, descriptions,
  schemas and annotations. This path works the same on **local URLs** (`localhost`,
  `127.0.0.1`, `*.local`, LAN addresses, any port) and **production URLs**, with no account and
  no tunnel.
- **External scan (optional, production URLs only).** Behind a setting, also call an outside
  scanner's HTTP API from Rust (not its `npx` CLI) and show its score next to Sawit's, labelled
  "External score" (name the service only if its terms require it). Don't send local or private
  URLs to it by default, and say why the external score is missing for those. Checks that need
  outside data Sawit can't get itself (search ranking, encyclopedia presence, registry listings)
  are skipped, or taken from the external results and marked as such.
- **Scoring.** Show scores per layer and in total, with the same layer weights and the same rules
  for checks that don't apply as the main reference scanner, so results are close to its own.
  Also show an "Essentials" score for content sites, and let the user pick the scan type
  (content site, API or app, all).
- **Report.** Each check shows pass, fail, warning or not applicable, the evidence (the URL
  fetched, the status, the header or a snippet), and a fix with a link to its spec. Add a "copy
  fix prompt for an agent" button.
- **MCP:** `browser_seo` (or the code-mode API) returns the same report and accepts `checks`,
  `scan_type` and `external: bool`.
- **Done when:** for kyzn.life and bahrul.me, Sawit's score is within a few points of the
  reference scanner's on the checks both run, and a dev server on `localhost` gets a full
  report.

1. **Design system:** tokens first: colors (with light and dark), type scale, spacing scale,
   radii, shadows, as canvas variables (`variable.create`, `variable.set`, `variable.import`).
2. **Reusable components:** buttons, inputs, cards, nav and so on, built from the tokens, with
   their variants and states side by side (`component.create`, `component.playground`), on a
   Components page.
3. **Screens and artboards:** each screen at a real device size, built from **instances** of the
   components and laid out with auto layout (`layout.add`), on its own page or section.
4. **Cover:** a cover artboard for the file (name, what it is, status, date), made last from the
   same tokens.

**Where things stand:** the engine already has variables, components and auto layout
(`crates/board/src`), with a Variables window, component properties and an Assets tab
(`1aa6b15`), and `canvas_design_guide` serves the design standard
(`crates/mcp/src/app/canvas/guide.rs`). Since `38c3cce` the standard also applies without the
agent asking (`crates/mcp/src/app/canvas/design.rs`): the session's first UI work in
`canvas_begin` answers with the standard's digest, later works with the sections they need, and
after each `canvas_screen_write` and on `canvas_progress {status: "done"}` Sawit runs **machine
checks** (`sawit_board::checks`, `crates/board/src/checks/`): text contrast (col.10, with
`contrast.py`'s formula **already ported to Rust**), target sizes (a11y.2), text size floors
(typ.11), the 4 px spacing scale (spc.1), missing alt and unnamed icon controls (a11y.7), field
labels and focus (a11y.8), `outline: none` with no ring (sta.8) and text that can't fit (lay.18).
Screens (`kind: "screen"`, HTML in `.nyawit/screens/`) are the default for UI. But the vector
tools still accept anything: raw hex colors, magic pixel sizes, one-off shapes copied ten times,
absolute positions, and screens with no system behind them. There is no `canvas_lint` tool, no
token binding, no component detection, no slop rules, no workflow state and no sketch mode.

- **Tokens over raw values.** Writes through `canvas_add_elements`, `canvas_update` and
  `canvas_command` take a token (`color: "fg/muted"`, `gap: "space/4"`) wherever they take a
  value. A raw value that matches a token is bound to it; one that matches none is a lint
  warning in the reply ("`#6b7280` is not in the system; nearest token `fg/muted`").
- **Components over copies.** When an agent adds a group shaped like an existing component, the
  reply says so and offers the instance. Repeated near-identical groups (three or more) are a
  lint warning with a "make this a component" command.
- **Layout.** Screens use auto layout; children of an auto-layout frame are not placed by
  absolute `x`/`y`. Spacing snaps to the spacing scale, sizes to the grid, text to the type
  scale. Artboards use the device sizes from D1.
- **A design lint, in Rust.** A new `canvas_lint` tool (and a lint summary in the reply of every
  write, kept short) checks the page against the standard in `sawit-canvas-design`: values off
  the tokens, detached or copied components, uneven spacing, misaligned edges, text below the
  contrast minimum (reuse `sawit_board::checks`' contrast, already in Rust), too many type sizes or colors on
  one screen, placeholder copy ("Lorem ipsum", "Click here", "Welcome to our platform"), and the
  usual slop signs: purple-to-blue gradients by default, emoji as icons, glassmorphism and
  glow everywhere, card-in-card nesting, centred everything, three identical feature cards.
  Each finding has the layer id, why, and the fix as a command. Rules and thresholds live in
  one table in `crates/board` (or `crates/core`), with the guide section each one comes from.
- **Workflow state.** `canvas_begin` (or a new `canvas_design_status`) reports where the file is
  in the workflow: no system yet, system without components, components ready, screens, cover.
  The tools warn, not refuse, when a step is skipped ("This screen uses no components; the
  file has none yet. Start with the design system."), so quick sketches and diagrams still work.
  A "sketch" mode on `canvas_begin` turns the warnings off for wireframes and diagrams.
- **Starter system.** A command that lays out a starter design system and component set from
  Sawit's own tokens (`skills/sawit-canvas-design/references/tokens.md`) or from a site's design
  (`browser_design`, `browser_export_design`), so an agent never starts from nothing.
- **Review.** `canvas_screen_get` and `canvas_export` can return the lint findings next to the
  image, so an agent checks its own work before saying it is done.
- **MCP:** every new tool and argument in the README's MCP table and in `canvas_design_guide`;
  `canvas_design_guide` points to the lint rule for each guideline.
- **Tests:** each lint rule on a small fixture (passes on a clean page, fires on a slop page),
  token binding of raw values, component detection, the workflow state, and sketch mode staying
  quiet.
- **Done when:** an agent asked for "a SaaS dashboard, settings and login screens" through MCP
  only produces, in order, a design system page, a components page, three screens built from
  instances with auto layout, and a cover; `canvas_lint` reports no errors on the result; and
  the same request without the hardening (old tools) scores clearly worse on the lint, with the
  numbers in the commit message.

## B17. Bug: screens on the canvas show black or half-drawn, and blurry

**What the user saw** (screenshot, 2026-11-07): three mobile screens side by side on the canvas.

- **"Progress / Mobile"** is drawn in full.
- **"Today / Mobile"** shows only its status bar, date line and the top half of the heading,
  cut through the middle of the letters ("Lower body B"). Below that the frame is solid near
  black down to the bottom.
- **"Session / Mobile"** stops after its header ("Back squat, Lift 1 of 4"); the rest is near
  black.
- **All three are soft and blurry**, as if a small picture were scaled up.

The same screens look right in Preview, so the page is fine. What the canvas paints is not.

**How a screen gets on the canvas** (`crates/app/src/board/web/mod.rs`):

- At rest, each screen is a WebKit snapshot drawn as a texture.
- The page first loads in a hidden view and "settles": fonts ready, finished animations ended,
  two frames drawn (`web/settle.rs`, `__sawitSettle`).
- A page that hasn't settled within `settle_ms` (3000 ms by default, `web/config.rs`) is
  snapshotted anyway.
- After an agent writes a screen, the build replay (`d905cfb`,
  `board/presence/replay/blueprint.rs`, `replay/marks.rs`) hides each changed element under a
  cover until its animation plays, then fades the cover out (`GO_LIVE`).

**Likely causes, to confirm before fixing** (each fits the picture; check them in this order):

1. **A snapshot taken before the page finished drawing.**
   - The near-black is the page's own background with its content not yet on it. This happens
     with entrance animations (elements starting at `opacity: 0` or clipped, revealed one
     after another), or with WebKit tiles not yet painted.
   - A heading cut through its letters points to a reveal clip, or a tile edge, caught
     mid-way.
   - If the settle times out, or `__sawitSettle` fires before the page's own animations, the
     half-drawn picture stays until something reloads the page.
2. **A build replay that never finished.**
   - Elements whose task never ran keep their cover (`progress` is `None`, so the cover is
     drawn fully).
   - A lane can stall or be dropped: a newer write to the same screen, the app or canvas
     reopened mid-build, more than 300 elements, the lane's queue cleared. The covered part
     then stays hidden.
   - Check whether the covers are drawn in the screen's background colour, and whether they
     outlive their lane.
3. **Blur:** the texture is a snapshot at one scale, drawn larger. Either it was taken at a low
   zoom and never retaken when the zoom settled (the pool's "snapshot again at a settled zoom",
   `web/pool.rs`), or `SAWIT_WEB_SCALE` / the default scale is below the display's at this
   zoom.

**How to find out:**

- Reproduce with an agent writing three screens one after another, with entrance animations
  on one of them. Also try reopening the canvas, and zooming out then back in.
- Read the `web` control op's `status` (the frames, their views, textures and readings) and
  take a `snapshot` of the broken frame (`web/ops.rs`). If a fresh snapshot is right, the
  picture was stale (cause 1 or 3). If the frame is still dark with a good texture, something
  is drawn over it (cause 2).

**Fix:**

- **Snapshot only a page that has finished drawing.**
  - Wait for the page's animations and transitions to end (`document.getAnimations()`
    finished, or none running) and for images to decode, as well as fonts and two frames.
  - Then check the snapshot isn't mostly one flat colour where the DOM has content, and take
    it again if so (with a limit).
  - On settle timeout, keep the previous good picture and take a new one when the page
    finishes, rather than keeping a half-drawn one.
  - Pages that animate for ever are snapshotted with animations paused at their end state
    (WebKit's reduced motion, or the page agent finishing them).
- **Covers can never outlive their build.**
  - When a lane is dropped, replaced by a newer write, or the canvas reloads, every cover it
    owned goes at once.
  - A cover also has a time limit after its write (for example `WRITTEN_WITHIN`, 30 s), after
    which the live page shows anyway.
  - A screen at rest is never covered.
- **Sharp at every zoom.** Take the snapshot again at the settled zoom × the display's scale
  (up to a cap), and paint it at that size. Never show an upscaled texture for longer than one
  settle.
- **A frame that isn't ready says so.** While its first good picture isn't there, show the
  "Loading…" pill route frames already use (`web/status.rs`), not a dark rectangle.

**Tests:**

- a page with staggered entrance animations is snapshotted only after they end;
- a mostly blank snapshot is retaken;
- a dropped or replaced build clears its covers;
- covers expire;
- a snapshot is retaken after zooming in;
- `canvas_screen_get` and `canvas_export` return the full screen, not the half-drawn texture.

**Done when:** an agent writes three screens in a row (one with entrance animations) and all
three show complete and sharp on the canvas at 45%, 100% and 200% zoom, after reopening the
canvas too, checked in the real app with `canvas_screen_get` and screenshots.

## C1. Track every agent and the account pool, in six views

**Reference, for research only:** the demo at https://headroom.theblank.club/demo/. Never name

It reads each account's usage limits every few minutes, records the history, and shows how much
room is left, when limits reset, which account to use next, and what it all costs. The demo runs
on made-up data. The notes below come from the demo's JavaScript bundle (`DetailedPage`,
`ComparePage`, `TimelinePage`, `AnalyticsPage`, `WalletPage` and the main page). Open the demo
in a browser and go through every view before you build.

**Rules for this item:**

  `canvas_design_guide`, `vendor/gpui-base` components). Design the screens on Sawit's canvas

- **100% Rust where possible.** The reference is a JavaScript web app; Sawit's version is

### The views

1. **Overview.** Every account at a glance: provider, plan, the share of each limit
   left (5-hour, weekly, credits), when it resets, and a status: Plenty Left, Running Low, Almost
   Out, Limit Reached, Not Reported, Out of Date, Refresh Failed, Sign-in Expired. Notifications
   (mark all as read), refresh, rename an account, and a "hold to reset" action for providers
   that allow it.
2. **Detailed.** One row per account, grouped **By Provider** or **By Urgency**, with a provider
   filter, a provider order changed by dragging, and a "Show limits as" switch (percent used or
   left, amount).
3. **Compare.** "Recommended right now": the account with the most room, why it was picked, the
   next best, and which limit holds each one back. Notes that percentages ignore plan size. Shows
   credit balances, accounts with no limit, and what isn't reported.
4. **Timeline.** Quota windows for each account on a time axis: the current window (time
   passed, room left), the next window (opens on reset, or on next use), earlier windows. Ranges
   such as Next 24 Hours and This Week. A Watch List (running low until…), Recent Resets (last 7
   days), and banked or saved resets with their expiry (expires soon, used before expiry, reset
   early).
5. **Wallet.** Money: cost per account (per month, per year, "included with" another
   subscription, price not set), list prices, top-ups (amount, credits added, expiry date and an
   alert before it, notes, detected from a balance rise), upcoming renewals (next 30 days, next
   month), paid top-ups per month for the last 6 months, subscriptions by account, removed
   accounts, and exchange rates.
6. **Analytics.** Over 30 or 90 days, for all accounts or one:
   - **Forecast:** current and recent pace against an even pace, projected use, runs out before
     reset or at reset with room to spare.
   - **Plan fit:** what could be downsized, cancelled or dropped, and an estimate of money left
     unused (price × share of the limit not used).
   - **Heatmaps:** weekday by hour, locked hours (darker: more often), busiest hour, the typical
     week, then one row per week.
   - **Windows:** how full each limit window got (one cell per window, width is its length),
     usage per window, peak per week, hit-the-limit counts, average active and average peak.
   - **"Move work" suggestions:** shift work from an account that runs out to one with room.
   - Sortable tables (select a header to sort, a row for detail).

# Part D: native screenshots and screen recordings for the browser, every size, full page, MCP

**Goal:** native Rust screenshots and screen recordings of the browser, at every device size

## Where things stand

- **Recordings are half native.** `Engine::capture_frame` takes each frame natively (at most

  back into the page as a JS `MediaStream`, and mesurer's JavaScript builds the MP4
  (`core/mp4-boxes.ts`). Rust then patches the file so AVFoundation opens it
  (`repair_mp4`, `crates/core/src/browser/mesurer/files/mp4.rs`). Recording is only started from
  the Annotate UI (`C V`, `crates/app/src/browser/annotate/view.rs:471`). **There is no MCP tool to
  record.**
- **Devices:** `crates/core/src/browser/viewport.rs` has six presets (iPhone 15 393×852, Pixel 8
  412×915, iPad mini 744×1133, iPad Pro 11″ 834×1194, Laptop 1280×800, Desktop 1440×900), used by
  the toolbar and `browser_resize`. The page is scaled to fit the tab, so a capture's pixel size
  today depends on the tab's size and the display's scale, not on the device that was picked.
- **MCP:** `browser_screenshot` (`crates/mcp/src/browser/mod.rs`, `ScreenshotArgs` in
  `args.rs:150`) takes `ref`, `selector`, `output_path`, `mesurer`, and `tab` (since browser tabs
  landed in `1605744`: a tab not on show is woken off screen), and returns a PNG only.
- **Status (2026-11-07):** nothing in Part D has started. `DEVICES` still has the six presets,
  `capture.rs` has no full-page or PDF path, `objc2-av-foundation` has only the `AVPlayer` /
  `AVAsset` features (no `AVAssetWriter`), and there is no `browser_record_*` tool.

## Goal

Every capture is made in Rust, through Apple's frameworks, with no JavaScript in the capture or
encoding path. Any device or size, from low resolution up to 4K, for the visible view or the

## D1. Sizes: every device class and every resolution

- **More device presets** in `DEVICES` (keep the six that exist; names are a suggestion):
  - Mobile: iPhone SE 375×667, iPhone 15 393×852, iPhone 15 Pro Max 430×932, Pixel 8 412×915,
    Galaxy S 360×780, small Android 320×568.
  - Tablet: iPad mini 744×1133, iPad Air 820×1180, iPad Pro 11″ 834×1194, iPad Pro 13″
    1032×1376, Android tablet 800×1280.
  - Laptop: 1280×800, 1366×768, 1440×900 (MacBook Air), 1512×982 (MacBook Pro 14″), 1536×864.
  - Desktop: 1920×1080 (Full HD), 2560×1440 (QHD), 3840×2160 (4K).
  - Group them as Mobile, Tablet, Laptop, Desktop in the toolbar menu and in MCP errors, with
    portrait and landscape for phones and tablets (the rotate already exists).
- **Separate the page's size from the output size.** A capture has:
  - a **viewport** in CSS px (the device or a width × height): what the page lays out to;
  - a **scale** (device pixel ratio): 1×, 2×, 3×, default the device's own (3× for phones, 2× for
    Apple tablets and laptops, 1× for 1080p desktops);
  - or an **output resolution** preset, for video: 360p, 480p, 720p (HD), 1080p (Full HD),
    1440p (QHD), 2160p (4K), or a max width. The viewport's aspect ratio is kept.
- **Capture at the chosen size, not the tab's.** The page must lay out at the device width even
  when the tab is narrower or wider, and the pixels must not depend on the display the window is
  on (a 1× external screen must still give a 3× phone shot). Options: render the `WKWebView` at
  the viewport size off screen or detached from the scaled-to-fit layer for the capture, and use
  `WKSnapshotConfiguration.snapshotWidth` = viewport width × scale. **Check** that WebKit
  re-rasterizes at that width instead of upscaling a blurry bitmap; if it doesn't, set the view's
  backing scale for the capture.
- **Limits to handle:** H.264 needs even width and height and tops out at 4096 px wide (use
  HEVC above that, or cap at 3840); very large images may fail (see D2 tiling). Warn when the
  requested size is bigger than what the page or encoder can give.
- **Done when:** the same page captured as each preset gives the expected pixel sizes, sharp at
  every scale, on a Retina screen and on a 1× external screen.

## D2. Full-page screenshot

- Capture the whole scrollable document, not just the visible part, at any device and scale
  from D1.
- **Approach, best first:**
  1. Make the web view as tall as the document (`document.scrollingElement.scrollHeight`, read
     once from JS), let it lay out, `takeSnapshot` with `rect` covering the whole view, then put
     the size back. One image, no seams.
  2. If a page is too tall for one snapshot (WebKit and Core Graphics fail on very large
     surfaces, roughly above 16k px on a side), take it in **tiles**: scroll, snapshot,
     repeat, and stitch the `CGImage`s in Rust (`CGContext` draw into one bitmap, or write
     straight to PNG in strips so a 30k px page doesn't need gigabytes of RAM).
  3. `WKWebView createPDFWithConfiguration:` (macOS 11+) as a vector option: a full-page PDF
     export is useful on its own; offer it as a format.
- **Page problems to handle:** `position: fixed`/`sticky` headers repeated in every tile (hide
  them after the first tile, or use approach 1); lazy-loaded images and infinite scroll (scroll
  through once first and wait for the network to go quiet, with a timeout and a max height);
  `100vh` sections that grow when the view is made tall (lock the `vh` to the device height);
  animations (wait a frame, or offer "pause animations"); scroll position restored afterwards.
- **Also:** a full-page capture of one element (`ref`/`selector`) that is itself scrollable.
- **Done when:** full-page shots of long real sites (apple.com, a docs site, one with a sticky
  header and lazy images) come out whole, without repeated headers or blank images, at mobile,
  tablet, laptop and desktop sizes.

## D3. Native video encoding (replace the JS muxer)

- Feed the frames from `capture_frame` into **AVAssetWriter** (`objc2-av-foundation`, already a
  dependency: turn on `AVAssetWriter`, `AVAssetWriterInput`,
  `AVAssetWriterInputPixelBufferAdaptor`), as `CVPixelBuffer`s with real presentation times. The
  Mac's hardware encoder (VideoToolbox) does H.264 or HEVC.
- Then `repair_mp4` and mesurer's JS muxer are no longer needed for Sawit's own recordings (keep
  mesurer's UI working: its recording button should call the native recorder through the bridge;
  see A2 and the "must stay JavaScript" list in Part A before removing anything).
- **Options:** format MP4 (H.264) by default, MOV (HEVC) for 4K or smaller files, GIF for short
  clips (encode in Rust, e.g. the `gif` crate, or `gifski` for better quality, with a frame and
  size cap); frame rate 15, 24, 30
  or 60; quality or bitrate; resolution from D1.
- **Frame timing:** `takeSnapshot` is slow (expect about 10–30 fps on a big view). Stamp each
  frame with when it was taken, don't assume a fixed rate, and report the real fps achieved.
- **Optional, later: a smooth 60 fps mode with ScreenCaptureKit** (`objc2-screen-capture-kit`,
  macOS 12.3+): an `SCStream` filtered to Sawit's window and cropped to the web view gives every
  frame from the GPU, including `<video>`, WebGL, CSS animation, the cursor and system audio.
  Costs: the Screen Recording permission prompt, and it records what is drawn over the page
  (popovers, overlays) unless those are excluded; it also needs the view on screen at its real
  size, so it can't record a device size bigger than the tab. Keep it opt-in.
- **Done when:** recordings open in QuickTime and Quick Look without repair, at every size in
  D1, and a 60-second 1080p recording doesn't drop the app below smooth UI.

## D4. Full-page recording

- "Record full page" = a scroll-through video: the recorder scrolls the page from top to bottom
  (and optionally back up) at a steady speed while recording, at the chosen device and size.
- **Options:** scroll speed (px per second) or total duration, pause at the top and bottom,
  scroll smoothly (native scrolling, A5) rather than jumping, wait for lazy content as in D2,
  stop at a max height.
- Also keep the normal modes: visible view, a region (as Annotate's `C V` does now), and one
  element.
- **Done when:** a full-page recording of a long site plays smoothly from top to bottom with
